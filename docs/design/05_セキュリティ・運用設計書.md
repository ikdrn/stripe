## 1. 設計目的（なぜこの設計が必要か）

### 1.1 決済システムにおけるセキュリティの重要性

決済システムは**最も攻撃対象になりやすい**システムである。

| 攻撃シナリオ | 結果 |
|-------------|------|
| Webhook偽装 | 不正にサービス取得、金銭的損失 |
| APIキー漏洩 | アカウント乗っ取り、不正決済 |
| SQLインジェクション | 顧客データ漏洩、改ざん |
| 中間者攻撃 | 決済情報の盗聴 |

**この設計書の目的**:
「攻撃されることを前提に、被害を最小化する」設計を記録する。

### 1.2 初心者が見落とす脆弱性

```typescript
// ❌ 危険な実装例

// 1. Webhook署名検証なし
app.post('/webhook', (req, res) => {
  const event = req.body;  // 誰でも偽イベントを送れる
  // ...

// 2. APIキーをコードに直書き
const stripe = new Stripe('sk_live_xxxxx');  // GitHubに公開されると終わり

// 3. 金額をクライアントから受け取る
```

### 4.2 Webhook セキュリティ

#### 署名検証の実装（再掲・詳細版）

```typescript
// infrastructure/stripe/webhook-verifier.ts

import Stripe from 'stripe';
import { Request, Response, NextFunction } from 'express';

/**
 * Webhook署名検証
 *
 * 攻撃シナリオ:
 * 1. 攻撃者が "/webhook" に偽の "payment_intent.succeeded" を送信
 * 2. 署名検証なしだと、サービスが不正に提供される
 *
 * 対策:
 * - Stripeが送信時に署名を付与
 * - サーバー側で署名を検証
 * - 署名が合わなければ拒否
 */
export function createWebhookMiddleware(
  stripe: Stripe,
  webhookSecret: string
) {
  return (req: Request, res: Response, next: NextFunction): void => {
    const signature = req.headers['stripe-signature'];

    // 署名ヘッダーがない場合は拒否
    if (!signature || typeof signature !== 'string') {
      res.status(400).json({
        error: 'Missing stripe-signature header',
      });
      return;
    }

    try {
      // 重要: req.body は raw buffer である必要がある
      // express.json() より前に express.raw() で受け取る
      const event = stripe.webhooks.constructEvent(
        req.body,
        signature,
        webhookSecret
      );

      // タイムスタンプ検証（リプレイ攻撃防止）
      const tolerance = 300; // 5分
      const eventTime = event.created;
      const now = Math.floor(Date.now() / 1000);

      if (now - eventTime > tolerance) {
        res.status(400).json({
          error: 'Webhook timestamp too old',
        });
        return;
      }

      // 検証済みイベントを添付
      (req as any).stripeEvent = event;
      next();
    } catch (error) {
      if (error instanceof Stripe.errors.StripeSignatureVerificationError) {
        res.status(400).json({
          error: 'Invalid signature',
        });
        return;
      }
      throw error;
    }
  };
}
```

#### Express設定（raw body取得）

```typescript
// presentation/app.ts

import express from 'express';

const app = express();

// Webhook用: raw bodyで受け取る（署名検証に必要）
app.use(
  '/api/webhook',
  express.raw({ type: 'application/json' }),
  createWebhookMiddleware(stripe, config.stripeWebhookSecret)
);

// その他のAPI: JSONパース
app.use(express.json());
```

### 4.3 入力検証

#### 金額改ざん防止

```typescript
// application/services/payment.service.ts

/**
 * 金額はサーバー側で計算する
 *
 * ❌ 危険: クライアントから金額を受け取る
 * POST /api/payment { amount: 100 }  // 本当は10000円の商品
 *
 * ✓ 安全: 商品IDから金額を取得
 * POST /api/payment { productId: 'prod_xxx' }
 */
async function createPaymentIntent(dto: CreatePaymentDto): Promise<PaymentIntent> {
  // 商品IDから正しい金額を取得
  const product = await productRepository.findById(dto.productId);
  if (!product) {
    throw new NotFoundError('Product not found');
  }

  // サーバー側で金額を決定
  const amount = product.price;

  return stripe.paymentIntents.create({
    amount,
    currency: 'jpy',
    metadata: {
      productId: product.id,
      userId: dto.userId,
    },
  });
}
```

#### DBスキーマ例

```sql
-- payments テーブル
CREATE TABLE payments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id),
    stripe_payment_intent_id VARCHAR(255) UNIQUE NOT NULL,
    stripe_customer_id VARCHAR(255),
    amount INTEGER NOT NULL,
    currency VARCHAR(3) NOT NULL DEFAULT 'jpy',
    status VARCHAR(50) NOT NULL DEFAULT 'pending',
    -- カード情報は保存しない。必要なら Stripe API から取得
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),

    -- インデックス

        status IN ('pending', 'processing', 'succeeded', 'failed', 'canceled')
    )
);

CREATE INDEX idx_payments_user_id ON payments(user_id);
CREATE INDEX idx_payments_stripe_pi_id ON payments(stripe_payment_intent_id);
CREATE INDEX idx_payments_status ON payments(status);
```

## 6. 代替案と、なぜ採用しなかったか

### 6.1 代替案A: 独自の暗号化でカード情報を保存

**不採用理由**:
- PCI DSS準拠が必要（年間数百万円のコスト）
- セキュリティリスクが飛躍的に増大
- Stripeを使う意味がなくなる

### 6.2 代替案B: Webhook署名検証をスキップ（開発効率重視）

**不採用理由**:
- 攻撃者が偽イベントでサービスを不正取得可能
- 「開発効率」は本番環境のセキュリティとトレードオフにならない
- Stripe CLIでローカル開発時も署名検証可能

### 6.3 代替案C: 全権限を持つAPIキー1つで運用

**不採用理由**:
- 漏洩時の影響が最大化
- 最小権限の原則に違反
- Restricted Keyの作成は簡単

## 7. 将来変更時に壊れやすいポイント

### 7.1 Webhook Secret のローテーション

```
影響: 署名検証が失敗し、全Webhookが拒否される
対策:
  - ローテーション時は新旧両方のSecretを一時的に受け入れる
  - Stripeは複数のWebhook Secretをサポート
```

### 7.2 新しいセキュリティ要件の追加

```
影響: 法改正や業界基準の変更
対策:
  - Stripeのセキュリティ関連ドキュメントを定期確認
  - 年1回のセキュリティレビューを実施
```

### 7.3 インフラ移行時

```
影響: シークレット管理の移行漏れ
対策:
  - シークレットの一覧を管理
  - 移行チェックリストにシークレット確認を含める
```
