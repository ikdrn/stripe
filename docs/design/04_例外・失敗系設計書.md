## 1. 設計目的（なぜこの設計が必要か）

### 1.1 失敗系設計の重要性

決済システムにおける失敗処理は、成功処理より**遥かに複雑で重要**である。

| 失敗処理の欠陥 | 結果 |
|---------------|------|
| エラー種別の判定ミス | リトライ可能なエラーを諦める、不可能なエラーを無限リトライ |
| 二重課金防止の不備 | ユーザーに複数回課金、返金対応の発生 |
| 障害時の回復手順なし | 長時間のサービス停止、データ不整合 |

**この設計書の目的**:
「何が起きても、最悪でも"正しく失敗する"」状態を作る。

### 1.2 初心者が陥る誤った設計

```typescript
// ❌ 最悪のエラーハンドリング
try {
  const result = await stripe.paymentIntents.create({...});
  return { success: true, data: result };
} catch (error) {
  return { success: false, error: 'エラーが発生しました' };
}
```

**問題点**:
1. エラーの種類を区別していない
2. リトライ可能かどうか不明
3. ユーザーへの案内が不可能
4. 運用者が原因を特定できない

## 2. 前提条件・制約

### 2.1 Stripeエラーの分類体系

Stripeのエラーは以下の階層で分類される：

```
Stripe Error
├── StripeCardError          (カード関連)
│   ├── card_declined        (カード拒否)
│   ├── expired_card         (有効期限切れ)
│   ├── incorrect_cvc        (CVC不正)
│   └── ...
├── StripeInvalidRequestError (リクエスト不正)
│   ├── parameter_missing    (パラメータ不足)
│   ├── parameter_invalid    (パラメータ不正)
│   └── ...
├── StripeAPIError           (Stripe側の問題)
├── StripeConnectionError    (ネットワーク問題)
├── StripeAuthenticationError(認証エラー)
└── StripeRateLimitError     (レートリミット)
```

### 2.2 エラー対応の判断軸

| エラー種別 | リトライ | ユーザーアクション | 運用者アクション |
|-----------|---------|------------------|----------------|
| CardError | 不可 | カード情報再入力 | なし |
| InvalidRequestError | 不可 | 不可（バグ） | 緊急修正 |
| APIError | 可 | 待機 | Stripe Status確認 |
| ConnectionError | 可 | 待機 | ネットワーク確認 |
| AuthenticationError | 不可 | 不可（バグ） | APIキー確認 |
| RateLimitError | 可（遅延） | 待機 | 負荷分散検討 |

## 3. 設計方針（採用した判断軸）

### 3.1 エラー処理の4原則

```
┌─────────────────────────────────────────────────────────┐
│              エラー処理の4原則                           │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ 1. 分類: エラーを正しく分類し、対応を分岐する            │
│                                                         │
│ 2. 記録: 全てのエラーを構造化ログに記録する              │
│                                                         │
│ 3. 通知: ユーザーには適切なメッセージ、運用者には詳細    │
│                                                         │
│ 4. 回復: リトライ可能なエラーは自動回復を試みる          │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 エラー情報の流れ

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Stripe    │───>│   Server    │───>│   Client    │
│  (詳細情報)  │    │ (分類/変換)  │    │(ユーザー向け)│
└─────────────┘    └──────┬──────┘    └─────────────┘
                          │
                          │ 詳細ログ
                          ▼
                   ┌─────────────┐
                   │  Logging    │
                   │  System     │
                   └─────────────┘
```

## 4. 構造・フロー説明

### 4.1 エラーハンドリング実装パターン

```typescript
// shared/errors/stripe-error-handler.ts

import Stripe from 'stripe';

/**
 * アプリケーション用エラー型
 * Stripeの詳細を隠蔽し、対応方針を明確化
 */
export type PaymentErrorType =
  | 'CARD_DECLINED'           // カード拒否
  | 'CARD_EXPIRED'            // 有効期限切れ
  | 'CARD_INVALID'            // カード情報不正
  | 'INSUFFICIENT_FUNDS'      // 残高不足
  | 'PROCESSING_ERROR'        // 処理エラー（リトライ可）
  | 'AUTHENTICATION_REQUIRED' // 追加認証必要
  | 'SYSTEM_ERROR'            // システムエラー
  | 'RATE_LIMITED'            // レートリミット
  | 'UNKNOWN';                // 不明

export interface PaymentError {
  type: PaymentErrorType;
  message: string;           // ユーザー向けメッセージ
  retryable: boolean;        // リトライ可能か
  userAction: string | null; // ユーザーが取るべきアクション
  stripeCode?: string;       // Stripeのエラーコード（ログ用）
  requestId?: string;        // Stripeのリクエストスト ID（調査用）
}

export function handleStripeError(error: unknown): PaymentError {
  // Stripeエラーでない場合
  if (!(error instanceof Stripe.errors.StripeError)) {
    return {
      type: 'UNKNOWN',
      message: 'システムエラーが発生しました',
      retryable: false,
      userAction: 'しばらく時間をおいて再度お試しください',
    };
  }

  const requestId = error.requestId;

  // カードエラー
  if (error instanceof Stripe.errors.StripeCardError) {
    return handleCardError(error, requestId);
  }

  // APIエラー（Stripe側の問題）
  if (error instanceof Stripe.errors.StripeAPIError) {
    return {
      type: 'PROCESSING_ERROR',
      message: '決済処理中にエラーが発生しました',
      retryable: true,
      userAction: '数分後に再度お試しください',
      stripeCode: error.code ?? undefined,
      requestId,
    };
  }

  // 接続エラー
  if (error instanceof Stripe.errors.StripeConnectionError) {
    return {
      type: 'PROCESSING_ERROR',
      message: '通信エラーが発生しました',
      retryable: true,
      userAction: 'インターネット接続を確認し、再度お試しください',
      requestId,
    };
  }

  // レートリミット
  if (error instanceof Stripe.errors.StripeRateLimitError) {
    return {
      type: 'RATE_LIMITED',
      message: 'アクセスが集中しています',
      retryable: true,
      userAction: 'しばらく時間をおいて再度お試しください',
      requestId,
    };
  }

  // 認証エラー（設定ミス）
  if (error instanceof Stripe.errors.StripeAuthenticationError) {
    return {
      type: 'SYSTEM_ERROR',
      message: 'システム設定エラーが発生しました',
      retryable: false,
      userAction: '管理者にお問い合わせください',
      requestId,
    };
  }

  // リクエスト不正（バグ）
  if (error instanceof Stripe.errors.StripeInvalidRequestError) {
    return {
      type: 'SYSTEM_ERROR',
      message: 'システムエラーが発生しました',
      retryable: false,
      userAction: '管理者にお問い合わせください',
      stripeCode: error.code ?? undefined,
      requestId,
    };
  }

  // 未知のStripeエラー
  return {
    type: 'UNKNOWN',
    message: 'エラーが発生しました',
    retryable: false,
    userAction: '管理者にお問い合わせください',
    requestId,
  };
}

function handleCardError(
  error: Stripe.errors.StripeCardError,
  requestId?: string
): PaymentError {
  const declineCode = error.decline_code;
  const code = error.code;

  // カード拒否の詳細分類
  if (code === 'card_declined') {
    switch (declineCode) {
      case 'insufficient_funds':
        return {
          type: 'INSUFFICIENT_FUNDS',
          message: '残高が不足しています',
          retryable: false,
          userAction: '別のカードをお試しいただくか、残高をご確認ください',
          stripeCode: declineCode,
          requestId,
        };
      case 'lost_card':
      case 'stolen_card':
        return {
          type: 'CARD_DECLINED',
          message: 'このカードはご利用いただけません',
          retryable: false,
          userAction: 'カード会社にお問い合わせください',
          stripeCode: declineCode,
          requestId,
        };
      default:
        return {
          type: 'CARD_DECLINED',
          message: 'カードが拒否されました',
          retryable: false,
          userAction: '別のカードをお試しください',
          stripeCode: declineCode,
          requestId,
        };
    }
  }

  if (code === 'expired_card') {
    return {
      type: 'CARD_EXPIRED',
      message: 'カードの有効期限が切れています',
      retryable: false,
      userAction: '有効なカードをご登録ください',
      stripeCode: code,
      requestId,
    };
  }

  if (code === 'incorrect_cvc' || code === 'invalid_cvc') {
    return {
      type: 'CARD_INVALID',
      message: 'セキュリティコードが正しくありません',
      retryable: false,
      userAction: 'カード裏面のセキュリティコードをご確認ください',
      stripeCode: code,
      requestId,
    };
  }

  // その他のカードエラー
  return {
    type: 'CARD_INVALID',
    message: 'カード情報に問題があります',
    retryable: false,
    userAction: 'カード情報をご確認のうえ、再度お試しください',
    stripeCode: code ?? undefined,
    requestId,
  };
}
```

### 4.2 リトライ戦略

```typescript
// infrastructure/stripe/retry-strategy.ts

interface RetryConfig {
  maxAttempts: number;
  baseDelayMs: number;
  maxDelayMs: number;
}

const DEFAULT_RETRY_CONFIG: RetryConfig = {
  maxAttempts: 3,
  baseDelayMs: 1000,
  maxDelayMs: 10000,
};

export async function withRetry<T>(
  operation: () => Promise<T>,
  config: RetryConfig = DEFAULT_RETRY_CONFIG
): Promise<T> {
  let lastError: unknown;

  for (let attempt = 1; attempt <= config.maxAttempts; attempt++) {
    try {
      return await operation();
    } catch (error) {
      lastError = error;

      // リトライ不可能なエラーは即座に投げる
      if (!isRetryable(error)) {
        throw error;
      }

      // 最後の試行なら投げる
      if (attempt === config.maxAttempts) {
        throw error;
      }

      // エクスポネンシャルバックオフ
      const delay = Math.min(
        config.baseDelayMs * Math.pow(2, attempt - 1),
        config.maxDelayMs
      );

      await sleep(delay);
    }
  }

  throw lastError;
}

function isRetryable(error: unknown): boolean {
  if (!(error instanceof Stripe.errors.StripeError)) {
    return false;
  }

  // リトライ可能なエラー種別
  return (
    error instanceof Stripe.errors.StripeAPIError ||
    error instanceof Stripe.errors.StripeConnectionError ||
    error instanceof Stripe.errors.StripeRateLimitError
  );
}

function sleep(ms: number): Promise<void> {
  return new Promise(resolve => setTimeout(resolve, ms));
}
```

### 4.3 Webhook失敗時の回復

```
┌─────────────────────────────────────────────────────────┐
│             Webhook失敗時の回復戦略                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ 1. Stripeは自動リトライする（最大3日間）                 │
│    - 初回失敗後: 即座にリトライ                          │
│    - 以降: 指数バックオフ（最大1時間間隔）               │
│                                                         │
│ 2. 自前での回復手段                                      │
│    - 定期バッチでStripeと状態を照合                      │
│    - 管理画面から手動で状態を同期                        │
│                                                         │
│ 3. アラート設定                                          │
│    - Webhook失敗が連続したら通知                         │
│    - 未処理イベントの滞留を監視                          │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### 定期照合バッチの設計

```typescript
// application/jobs/payment-reconciliation.job.ts

/**
 * 決済状態照合バッチ
 *
 * 目的: Webhook取りこぼしによる状態不整合を検出・修復
 * 実行頻度: 1時間ごと
 */
export async function reconcilePayments(): Promise<void> {
  // 1. 「処理中」のまま一定時間経過したレコードを取得
  const stalePayments = await paymentRepository.findStale({
    status: 'processing',
    olderThan: new Date(Date.now() - 30 * 60 * 1000), // 30分以上前
  });

  for (const payment of stalePayments) {
    // 2. Stripeから最新状態を取得
    const stripePI = await stripe.paymentIntents.retrieve(
      payment.stripePaymentIntentId
    );

    // 3. 状態が異なれば更新
    if (stripePI.status !== payment.status) {
      logger.warn('Payment status mismatch detected', {
        paymentId: payment.id,
        localStatus: payment.status,
        stripeStatus: stripePI.status,
      });

      await paymentRepository.updateStatus(payment.id, stripePI.status);

      // 4. 必要なら後続処理を実行
      if (stripePI.status === 'succeeded') {
        await serviceProvisionService.provision(payment);
      }
    }
  }
}
```

## 5. Stripe特有の思想との対応関係

### 5.1 Idempotency Key によるリトライ安全性

```
┌─────────────────────────────────────────────────────────┐
│                 Idempotency Key の重要性                 │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ 問題: ネットワークエラーで「成功したか不明」な状態       │
│                                                         │
│ Client → Server: 決済リクエスト                         │
│ Server → Stripe: PaymentIntent作成                      │
│ Stripe → Server: (ネットワークエラーでレスポンス不達)    │
│                                                         │
│ この時、サーバーは「成功したか失敗したか」分からない     │
│ リトライすると二重課金のリスク                          │
│                                                         │
│ 解決: Idempotency Key                                   │
│ - 同じキーで再リクエスト → 同じ結果が返る               │
│ - 二重作成されない                                      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### Idempotency Key の生成戦略

```typescript
// shared/utils/idempotency.ts

/**
 * Idempotency Keyの生成
 *
 * 要件:
 * 1. 同一操作に対して同じキーを生成する
 * 2. 異なる操作に対して異なるキーを生成する
 * 3. 推測困難である
 */
export function generateIdempotencyKey(params: {
  userId: string;
  action: 'create_payment' | 'create_subscription';
  resourceId: string;  // 商品ID、プランID等
  timestamp?: number;  // オプション: リトライ時は同じタイムスタンプ
}): string {
  const base = [
    params.userId,
    params.action,
    params.resourceId,
    params.timestamp ?? Date.now(),
  ].join(':');

  return crypto
    .createHash('sha256')
    .update(base)
    .digest('hex')
    .slice(0, 32);
}
```

### 5.2 Webhook署名検証の必須性

```typescript
// presentation/middleware/stripe-webhook.middleware.ts

/**
 * Webhook署名検証ミドルウェア
 *
 * なぜ必須か:
 * 1. 攻撃者が偽のイベントを送信可能
 * 2. 「決済成功」の偽イベントでサービス不正取得
 * 3. 署名検証なしは重大なセキュリティホール
 */
export function verifyStripeWebhook(
  req: Request,
  res: Response,
  next: NextFunction
): void {
  const signature = req.headers['stripe-signature'];
  const webhookSecret = config.stripe.webhookSecret;

  if (!signature) {
    logger.warn('Webhook received without signature');
    res.status(400).json({ error: 'Missing signature' });
    return;
  }

  try {
    // req.body は raw body である必要がある
    const event = stripe.webhooks.constructEvent(
      req.body,  // raw body (Buffer)
      signature,
      webhookSecret
    );

    // 検証済みイベントをリクエストに添付
    req.stripeEvent = event;
    next();
  } catch (error) {
    logger.error('Webhook signature verification failed', { error });
    res.status(400).json({ error: 'Invalid signature' });
  }
}
```

## 6. 代替案と、なぜ採用しなかったか

### 6.1 代替案A: 全エラーを同一扱い

```typescript
// ❌ 全エラーを同じ扱い
catch (error) {
  return { error: 'エラーが発生しました' };
}
```

**不採用理由**:
- ユーザーが適切な対処を取れない
- リトライ可能なエラーを諦めてしまう
- 運用者が原因を特定できない

### 6.2 代替案B: Stripeエラーをそのままクライアントに返す

**不採用理由**:
- 内部実装の詳細が漏洩する
- 英語メッセージがそのまま表示される
- 攻撃者にヒントを与える

### 6.3 代替案C: リトライを無限に行う

**不採用理由**:
- リトライ不可能なエラーで無限ループ
- サーバーリソースの浪費
- Stripeレートリミットに抵触

## 7. 将来変更時に壊れやすいポイント

### 7.1 新しいエラーコードの追加

```
影響: 未知のエラーコードが「UNKNOWN」に分類される
対策:
  - Stripeのchangelogを定期確認
  - 「UNKNOWN」の発生をモニタリング
  - フォールバックを適切に設計
```

### 7.2 Stripeのリトライポリシー変更

```
影響: 自前リトライとStripeリトライが競合する可能性
対策:
  - Idempotency Keyで二重実行を防止
  - Stripeのドキュメントを定期確認
```

### 7.3 ログ形式の変更

```
影響: 監視・アラートが動作しなくなる
対策:
  - ログスキーマを定義し、変更時は移行計画を立てる
  - 構造化ログを使用し、パース処理を安定させる
```
