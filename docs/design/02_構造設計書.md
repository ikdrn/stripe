# 構造設計書：責務分離と依存関係

> 作成日: 2026-01-30
> 前提ドキュメント: [01_概要設計書.md](./01_概要設計書.md)

---

## 1. 設計目的（なぜこの設計が必要か）

### 1.1 構造設計の必要性

Stripe決済システムにおいて、**責務の曖昧さ**は以下の破綻を引き起こす：

| 破綻パターン | 原因 | 結果 |
|-------------|------|------|
| 決済ロジックの散在 | 「どこで何をするか」が不明確 | 二重課金、課金漏れ |
| Stripe依存の伝播 | ビジネスロジックがStripe APIに直接依存 | テスト困難、ベンダーロックイン |
| Webhook処理の肥大化 | 1つのWebhookハンドラに全処理を記述 | 保守不能、バグの温床 |

本設計書は、**責務を明確に分離**し、**依存方向を一方向に制御**することで、これらの破綻を構造的に防ぐ。

---

## 2. 前提条件・制約

### 2.1 レイヤードアーキテクチャの採用

本システムは**4層レイヤードアーキテクチャ**を採用する。

```
┌─────────────────────────────────────────────────────────┐
│                  Presentation Layer                     │
│            （API Routes / Controllers）                  │
├─────────────────────────────────────────────────────────┤
│                  Application Layer                      │
│              （Use Cases / Services）                    │
├─────────────────────────────────────────────────────────┤
│                    Domain Layer                         │
│           （Entities / Domain Services）                 │
├─────────────────────────────────────────────────────────┤
│                Infrastructure Layer                     │
│        （Stripe SDK / Database / External APIs）         │
└─────────────────────────────────────────────────────────┘
```

### 2.2 依存方向の絶対ルール

```
上位層 → 下位層 : 許可
下位層 → 上位層 : 禁止（依存性逆転で対応）

Presentation → Application → Domain ← Infrastructure
                                ↑
                          依存性逆転
```

## 3. 設計方針（採用した判断軸）

### 3.1 なぜレイヤードアーキテクチャか

#### 初心者が選びがちな誤った設計

```typescript
// ❌ 誤った設計：API RouteでStripeを直接呼び、DBも直接操作
app.post('/api/payment', async (req, res) => {
  const { amount, userId } = req.body;

  // Stripe API直接呼び出し
  const paymentIntent = await stripe.paymentIntents.create({
    amount,
    currency: 'jpy',
  });

  // DB直接操作
  await db.query(
    'UPDATE users SET payment_status = $1 WHERE id = $2',
    ['processing', userId]
  );

  res.json({ clientSecret: paymentIntent.client_secret });
});
```

**この設計の問題点**:

1. **テスト不能**: Stripeをモックするには、ルート全体をモックする必要がある
2. **責務混在**: HTTP処理、ビジネスロジック、外部API呼び出しが混在
3. **変更困難**: Stripe APIの仕様変更時、全ルートを修正する必要がある
4. **重複発生**: 同じStripe呼び出しが複数箇所に散在しやすい

#### 採用する設計

```typescript
// ✅ 正しい設計：責務を分離

// Presentation Layer（薄く保つ）
app.post('/api/payment', async (req, res) => {
  const result = await paymentService.initiatePayment(req.body);
  res.json(result);
});

// Application Layer（ユースケースの実現）
class PaymentService {
  constructor(
    private stripeGateway: PaymentGateway,
    private paymentRepository: PaymentRepository
  ) {}

  async initiatePayment(dto: InitiatePaymentDto) {
    const paymentIntent = await this.stripeGateway.createPaymentIntent(dto);
    await this.paymentRepository.savePaymentIntent(paymentIntent);
    return { clientSecret: paymentIntent.clientSecret };
  }
}

// Infrastructure Layer（外部依存を隠蔽）
class StripePaymentGateway implements PaymentGateway {
  async createPaymentIntent(dto: InitiatePaymentDto) {
    const intent = await stripe.paymentIntents.create({...});
    return this.toDomainModel(intent);
  }
}
```

### 4.2 各レイヤーの責務定義

#### Presentation Layer

| 責務 | 説明 |
|------|------|
| HTTPリクエストの受信 | Express/Fastifyのルート定義 |
| バリデーション | 入力値の形式チェック |
| 認証・認可 | ユーザー認証、権限チェック |
| レスポンス整形 | Application Layerの結果をJSON化 |

**やってはいけないこと**:
- ビジネスロジックの実装
- Stripe SDKの直接呼び出し
- DBへの直接アクセス

#### Application Layer

| 責務 | 説明 |
|------|------|
| ユースケースの実現 | 「決済を開始する」「サブスクを作成する」等 |
| トランザクション制御 | 複数操作のアトミック性確保 |
| Domain/Infrastructure の協調 | 各層を組み合わせてユースケースを実現 |

**やってはいけないこと**:
- HTTP固有の処理（ヘッダー操作等）
- Stripe SDKの直接呼び出し
- SQL文の直接記述

#### Domain Layer

| 責務 | 説明 |
|------|------|
| ビジネスルールの表現 | 「この状態では決済できない」等のルール |
| エンティティの定義 | Payment, Subscription, Customer等 |
| リポジトリ/ゲートウェイのインターフェース定義 | 実装は持たない |

**やってはいけないこと**:
- 外部サービスへの依存
- DBスキーマへの依存
- フレームワーク固有の機能への依存

#### Infrastructure Layer

| 責務 | 説明 |
|------|------|
| Stripe SDK操作 | PaymentIntent作成、Webhook解析等 |
| DB操作 | SQLクエリ、ORM操作 |
| Domain Layerインターフェースの実装 | Repository, Gatewayの具象クラス |

## 5. Stripe特有の思想との対応関係

### 5.1 Stripe Gateway の設計

Stripeとのやり取りを**Gateway**パターンで抽象化する理由：

```
┌─────────────────────────────────────────────────────────┐
│                    なぜGatewayで抽象化するか              │
├─────────────────────────────────────────────────────────┤
│ 1. Stripe SDKの変更に強くなる                            │
│    - SDK v10 → v11 の変更が局所化される                  │
│                                                         │
│ 2. テスト時にモック可能                                   │
│    - 実際のStripe APIを叩かずにテスト可能                 │
│                                                         │
│ 3. 将来の決済プロバイダ変更に対応                         │
│    - PayPal, Square等への差し替えが可能                  │
└─────────────────────────────────────────────────────────┘
```

#### Gateway インターフェース定義

```typescript
// domain/gateways/payment.gateway.ts

export interface PaymentGateway {
  createPaymentIntent(params: CreatePaymentIntentParams): Promise<PaymentIntent>;
  retrievePaymentIntent(id: string): Promise<PaymentIntent>;
  cancelPaymentIntent(id: string): Promise<PaymentIntent>;
}

export interface CreatePaymentIntentParams {
  amount: number;
  currency: string;
  customerId?: string;
  metadata?: Record<string, string>;
  idempotencyKey: string;  // 必須にして強制する
}
```

### 5.2 Webhook処理の構造

Webhook処理は**イベントディスパッチ**パターンを採用する。

```
┌─────────────────────────────────────────────────────────┐
│                Webhook処理の流れ                         │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Stripe → Webhook Route → Webhook Service → Event Handler │
│                  │              │               │        │
│            署名検証        イベント分岐      具体処理      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**なぜこの構造か**:

1. **署名検証の一元化**: Presentation Layerで完結
2. **イベント種別の判定**: Application Layerで分岐
3. **具体処理の分離**: 各イベントハンドラが単一責務

## 6. 代替案と、なぜ採用しなかったか

### 6.1 代替案A: クリーンアーキテクチャ（Onion Architecture）

**不採用理由**:
- 本プロジェクトの規模では過剰
- 4層で十分な関心の分離が達成可能
- 学習コストとメンテナンスコストのバランス

**将来採用する条件**:
- チーム規模が5人以上になった場合
- マイクロサービス化を検討する場合

### 6.2 代替案B: レイヤーなしのシンプル構造

```
src/
├── routes/
├── models/
└── utils/
```

**不採用理由**:
- Stripe依存が全体に伝播する
- テストが困難
- 将来の変更コストが指数的に増大

### 6.3 代替案C: マイクロサービス

**不採用理由**:
- 個人開発〜小規模チームでは運用コストが過大
- モノリスで十分な段階

**将来採用する条件**:
- 決済処理のスケールが必要になった場合
- 他サービスとの分離が必要になった場合

## 7. 将来変更時に壊れやすいポイント

### 7.1 レイヤー違反の検出

| 違反パターン | 検出方法 | 対策 |
|-------------|---------|------|
| Presentation → Infrastructure直接参照 | ESLintルール | import制限設定 |
| Domain → Infrastructure依存 | 依存グラフ分析 | 定期的なレビュー |
| 循環依存 | TypeScriptコンパイラ | barrel fileの慎重な使用 |

### 7.2 Stripe SDK バージョンアップ時

```
影響範囲: infrastructure/stripe/ のみ
確認事項:
  - 型定義の変更
  - メソッドシグネチャの変更
  - 非推奨APIの使用箇所
```

### 7.3 DBスキーマ変更時

```
影響範囲: infrastructure/database/ のみ
確認事項:
  - Entityとの整合性
  - マイグレーションの安全性
  - Stripe側データとの整合性
```

```
                    │ presentation │
                    └──────┬───────┘
                           │ depends on
                           ▼
                    ┌──────────────┐
                    │ application  │
                    └──────┬───────┘
                           │ depends on
                           ▼
                    ┌──────────────┐
          ┌─────────│    domain    │─────────┐
          │         └──────────────┘         │
          │ implements              implements│
          ▼                                   ▼
   ┌─────────────┐                    ┌─────────────┐
   │   stripe    │                    │  database   │
   │  (infra)    │                    │  (infra)    │
   └─────────────┘                    └─────────────┘
```
