# シーケンス設計書：状態遷移とイベントフロー

> 作成日: 2026-01-30
> 前提ドキュメント: [01_概要設計書.md](./01_概要設計書.md), [02_構造設計書.md](./02_構造設計書.md)

---

## 1. 設計目的（なぜこの設計が必要か）

### 1.1 シーケンス設計の必要性

Stripe決済において、**状態遷移の理解不足**は以下の破綻を引き起こす：

| 破綻パターン | 原因 | 結果 |
|-------------|------|------|
| 3Dセキュア途中離脱 | 中間状態を考慮していない | 永遠に「処理中」のまま放置 |
| 二重課金 | 再試行時の状態チェック漏れ | ユーザーから複数回課金 |
| Webhook処理漏れ | イベントの順序を仮定 | 状態不整合 |

本設計書は、**Stripeの状態遷移モデル**を正確に理解し、**あらゆる経路**を網羅した設計を記録する。

## 2. 前提条件・制約

### 2.1 Stripeの非同期性

```
┌─────────────────────────────────────────────────────────┐
│                    重要な前提                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  「APIレスポンス = 最終状態」ではない                     │
│                                                         │
│  理由：                                                  │
│  - 3Dセキュア認証は別ウィンドウで実行される               │
│  - 銀行処理は数日かかることがある                         │
│  - 不正検知で事後的にキャンセルされることがある            │
│                                                         │
│  結論：                                                  │
│  状態確定は Webhook でのみ行う                           │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.2 対象とする決済フロー

本設計書では以下のフローを対象とする：

1. **単発決済（PaymentIntent）** - 商品購入等
2. **サブスクリプション（Subscription）** - 月額課金等
3. **SetupIntent** - カード登録のみ（課金なし）

## 3. 設計方針（採用した判断軸）

### 3.1 状態管理の原則

```
┌─────────────────────────────────────────────────────────┐
│                  状態管理の3原則                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ 1. Stripeの状態を「正」とする                            │
│    → 自前DBの状態とStripe状態が矛盾したら、Stripeを信じる  │
│                                                         │
│ 2. 「処理中」を正しく表現する                            │
│    → succeeded/failed 以外は全て「未確定」として扱う       │
│                                                         │
│ 3. 状態遷移は Webhook で駆動する                         │
│    → クライアントレスポンスでの状態更新は「楽観的UI」のみ  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 4.4 Webhook イベント一覧と処理

#### 必須で処理すべきイベント

| イベント | 発生タイミング | 処理内容 |
|---------|---------------|---------|
| `payment_intent.succeeded` | 決済成功時 | サービス提供開始 |
| `payment_intent.payment_failed` | 決済失敗時 | ユーザー通知、リトライ案内 |
| `customer.subscription.created` | サブスク作成時 | サブスク状態の記録 |
| `customer.subscription.updated` | プラン変更等 | サブスク状態の更新 |
| `customer.subscription.deleted` | サブスク解約時 | サービス停止処理 |
| `invoice.paid` | 請求書支払い完了 | 次回課金日の更新 |
| `invoice.payment_failed` | 請求書支払い失敗 | リトライ/督促処理 |

#### 処理の冪等性保証

```typescript
// Webhookハンドラの冪等性確保パターン

async function handlePaymentIntentSucceeded(event: Stripe.Event) {
  const paymentIntent = event.data.object as Stripe.PaymentIntent;

  // 1. 既に処理済みかチェック
  const existingRecord = await paymentRepository.findByStripeId(paymentIntent.id);

  if (existingRecord?.status === 'succeeded') {
    // 既に成功処理済み → 何もしない（冪等）
    logger.info('Already processed', { paymentIntentId: paymentIntent.id });
    return;
  }

  // 2. イベントIDで重複チェック（より厳密）
  const processed = await eventLogRepository.exists(event.id);
  if (processed) {
    logger.info('Event already processed', { eventId: event.id });
    return;
  }

  // 3. トランザクション内で処理
  await db.transaction(async (tx) => {
    await paymentRepository.updateStatus(tx, paymentIntent.id, 'succeeded');
    await eventLogRepository.save(tx, event.id);
    await serviceProvisionService.provision(tx, paymentIntent.metadata);
  });
}
```

## 5. Stripe特有の思想との対応関係

### 5.1 `payment_behavior` の選択

サブスクリプション作成時の `payment_behavior` は設計上重要な選択点である。

| 値 | 動作 | 採用判断 |
|---|-----|---------|
| `default_incomplete` | 決済完了までincomplete状態 | **採用** |
| `error_if_incomplete` | 決済失敗時にエラー | 不採用（UX悪化） |
| `allow_incomplete` | 決済失敗でも作成 | 不採用（未払いユーザー発生） |

**`default_incomplete` を採用する理由**:
- 3Dセキュアフローに対応可能
- 決済完了までサービス提供しない（安全）
- クライアント側で決済完了を制御可能

### 5.2 Webhookの順序保証について

```
┌─────────────────────────────────────────────────────────┐
│                    重要な警告                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Webhook の到達順序は保証されない                        │
│                                                         │
│  例：                                                    │
│  1. payment_intent.succeeded が先に届く                 │
│  2. customer.subscription.created が後から届く          │
│                                                         │
│  対策：                                                  │
│  - 各イベントを独立して処理可能な設計にする              │
│  - 「このイベントが来ていないと処理できない」を避ける     │
│  - 必要なら Stripe API で最新状態を取得する              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 6. 代替案と、なぜ採用しなかったか

### 6.1 代替案A: ポーリングで状態確認

```
Client → Server: 決済状態確認（3秒ごと）
Server → Stripe: PaymentIntent取得
Server → Client: 現在の状態
```

**不採用理由**:
- APIレートリミットに抵触するリスク
- サーバー負荷が高い
- リアルタイム性がWebhookに劣る

**例外的に採用するケース**:
- Webhook障害時のフォールバック
- 管理画面での手動確認

### 6.2 代替案B: クライアントで直接Stripe状態を監視

**不採用理由**:
- サーバー側の状態と不整合が発生
- セキュリティリスク（クライアント側での判定は改ざん可能）

### 6.3 代替案C: 同期的に決済完了を待つ

```typescript
// ❌ やってはいけない
const result = await stripe.paymentIntents.confirm(id);
if (result.status === 'succeeded') {
  // サービス提供
}
```

**不採用理由**:
- 3Dセキュア時にタイムアウトする
- `requires_action` 状態でブロックされる
- Stripeの非同期設計思想に反する

## 7. 将来変更時に壊れやすいポイント

### 7.1 新しいWebhookイベントの追加

```
影響: 新しいイベントタイプの処理漏れ
対策:
  - 未知のイベントはログに記録して無視
  - 定期的にStripeのchangelogを確認
  - Webhook受信ログの監視
```

### 7.2 PaymentIntent状態の追加

```
影響: 新しい中間状態が追加される可能性
対策:
  - switch-caseでdefaultを必ず設ける
  - 未知の状態は「処理中」として扱う
```

### 7.3 3Dセキュア以外の認証フロー

```
影響: 新しい認証方式への対応
対策:
  - requires_action を汎用的に処理
  - next_action の具体的な内容に依存しすぎない
```

## 付録：状態遷移のテストケース

| ケース | 初期状態 | イベント | 期待される最終状態 |
|-------|---------|---------|-------------------|
| 正常決済 | requires_payment_method | succeeded | succeeded |
| 3DS成功 | requires_action | succeeded | succeeded |
| 3DS失敗 | requires_action | payment_failed | requires_payment_method |
| カード拒否 | requires_confirmation | payment_failed | requires_payment_method |
| 手動キャンセル | processing | canceled | canceled |
| タイムアウト | requires_action | (なし) | requires_action → canceled |
