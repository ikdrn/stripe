# 概要設計書：Stripe決済システム

> 作成日: 2026-01-30
> 対象読者: 将来の保守担当者、第三者開発者、法人化後のチームメンバー

---

## 1. 設計目的（なぜこの設計が必要か）

### 1.1 本設計書の存在意義

この設計書は「どう実装するか」ではなく「**なぜこの設計でなければ破綻するか**」を記録する。

Stripe決済システムにおいて、初心者が陥りやすい設計ミスは以下の3つである：

1. **決済成功をクライアントのレスポンスで判定する** → 二重課金・取りこぼしが発生
2. **自前DBに「課金済みフラグ」を持ち、それを正とする** → Stripeとの状態不整合
3. **同期的なリクエスト-レスポンスモデルで設計する** → 3Dセキュア等の非同期フローで破綻

本設計は、これらの破綻パターンを**構造的に防ぐ**ことを目的とする。

### 1.2 ビジネス目的

- SaaS型サービスにおけるサブスクリプション課金の実現
- 単発決済（追加機能購入等）への対応
- 将来的な従量課金への拡張可能性の確保

## 2. 前提条件・制約

### 2.1 Stripe APIの本質的制約

| 制約 | 説明 | 設計への影響 |
|------|------|-------------|
| **非同期性** | 決済完了は即時ではない（3Dセキュア、銀行処理等） | Webhookベースの状態管理が必須 |
| **冪等性要件** | 同一リクエストの再送が発生しうる | Idempotency Keyの設計が必要 |
| **状態の正（Source of Truth）** | 決済状態の正はStripe側にある | 自前DBは「キャッシュ」として扱う |
| **Webhook署名検証** | セキュリティ上必須 | 署名検証なしのWebhook受信は脆弱性 |

### 2.2 SCA（Strong Customer Authentication）要件

欧州PSD2規制により、多くの決済で追加認証が必要になる。これは日本国内ユーザーでも、カード発行会社の判断で発生しうる。

**設計上の帰結**: 決済フローは必ず「中断→再開」可能な設計にする必要がある。

### 2.3 技術スタック前提

| レイヤー | 選定技術 | 選定理由 |
|---------|---------|---------|
| バックエンド | Node.js + TypeScript | Stripe公式SDKの第一級サポート、型安全性 |
| フロントエンド | React | Stripe Elements/Payment Elementとの統合が容易 |
| データベース | PostgreSQL | ACID特性、JSON型サポート、拡張性 |
| インフラ | 未定（設計上は抽象化） | クラウド非依存の設計とする |

## 3. 設計方針（採用した判断軸）

### 3.1 根本方針：「Stripeを正とし、自前システムは従とする」

```
┌─────────────────────────────────────────────────────────┐
│                    設計の大原則                          │
│                                                         │
│   Stripe = 決済状態の Single Source of Truth           │
│   自前DB = Stripeの状態を「参照」するキャッシュ          │
│                                                         │
│   決済成功の判定 = Webhookイベントのみで行う             │
│   クライアントレスポンス = 「成功かもしれない」程度      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 なぜこの方針でないと破綻するか

#### 破綻パターン1: クライアントレスポンスで成功判定

```
[誤った設計]
Client → Server: 決済リクエスト
Server → Stripe: PaymentIntent作成
Stripe → Server: 成功レスポンス
Server → DB: 「課金済み」フラグON  ← ここが問題
Server → Client: 成功

[何が起きるか]
- 3Dセキュア認証中にユーザーがブラウザを閉じる
- Stripeでは「未完了」、自前DBでは「課金済み」
- サービス提供してしまい、売上未回収
```

#### 破綻パターン2: 自前DBを正とする

```
[誤った設計]
- 自前DBに payment_status カラムを持つ
- 定期的にStripeと「同期」する

[何が起きるか]
- 同期タイミングのズレで不整合
- 同期処理のバグで大量の不整合
- 「どちらが正しいか」の判断が不可能に
```

### 3.3 採用する設計パターン

| パターン | 説明 |
|---------|------|
| **イベント駆動** | Webhookを起点に状態遷移 |
| **楽観的UI** | クライアントには「処理中」を返し、確定はWebhookで |
| **冪等性保証** | 同一イベントの複数回処理を安全に |
| **参照キャッシュ** | 自前DBはStripe IDと最小限のメタデータのみ |

## 4. 構造・フロー説明

### 4.1 システム全体像

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   Client     │     │   Server     │     │   Stripe     │
│  (React)     │     │  (Node.js)   │     │   (API)      │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
       │ 1. 決済開始要求    │                    │
       │───────────────────>│                    │
       │                    │ 2. PaymentIntent   │
       │                    │    作成            │
       │                    │───────────────────>│
       │                    │                    │
       │                    │ 3. client_secret   │
       │                    │<───────────────────│
       │ 4. client_secret   │                    │
       │<───────────────────│                    │
       │                    │                    │
       │ 5. Stripe.js で決済確定                 │
       │────────────────────────────────────────>│
       │                    │                    │
       │                    │ 6. Webhook         │
       │                    │    (payment_intent │
       │                    │     .succeeded)    │
       │                    │<───────────────────│
       │                    │                    │
       │                    │ 7. DB更新          │
       │                    │    (状態確定)      │
       │                    │                    │
```

### 4.2 責務の明確な分離

| コンポーネント | 責務 | やってはいけないこと |
|---------------|------|---------------------|
| **Client** | UI表示、Stripe.jsへの橋渡し | 決済成功の判定、機密情報の保持 |
| **Server** | PaymentIntent作成、Webhook処理 | client_secretの保存、カード情報の受信 |
| **Database** | Stripe IDの保存、ビジネスデータとの紐付け | 決済状態の「正」としての保持 |

## 5. Stripe特有の思想との対応関係

### 5.1 PaymentIntentの設計思想

Stripeは `PaymentIntent` を「決済の意図」として設計している。これは：

- **作成時点では課金されない**（意図の表明のみ）
- **確定（confirm）は別操作**（クライアント側で実行可能）
- **状態遷移はStripeが管理**（`requires_payment_method` → `requires_confirmation` → `succeeded`）

この思想に従い、サーバーは「意図の作成」のみを担当し、「確定」はクライアントに委ねる。

### 5.2 Webhookの設計思想

Stripeは「最終的な状態通知はWebhookで行う」という思想を持つ。これは：

- **APIレスポンスは「その時点の状態」**（最終状態とは限らない）
- **Webhookは「状態確定の通知」**（信頼できる情報源）
- **Webhookは複数回届きうる**（冪等性が必須）

## 6. 代替案と、なぜ採用しなかったか

### 6.1 代替案A: Charges API を使う

**不採用理由**:
- Charges APIは旧API（非推奨ではないが、新機能はPaymentIntentに集中）
- SCA対応が困難
- 将来的なStripeの方針と乖離するリスク

### 6.2 代替案B: サーバーサイドで決済を完結させる

**不採用理由**:
- カード情報がサーバーを経由する（PCI DSS準拠が必要）
- 3Dセキュア等の追加認証フローに対応困難
- Stripeの推奨設計と乖離

### 6.3 代替案C: Stripe Checkoutを使う（ホスト型）

**条件付き採用可能**:
- 最も簡単で安全な選択肢
- ただしUI/UXのカスタマイズに制限
- MVP段階ではこちらを推奨、後にPayment Elementへ移行可能

**本設計書ではPayment Element（埋め込み型）を前提とするが、Checkoutへの差し替えは容易な設計とする**

## 7. 将来変更時に壊れやすいポイント

### 7.1 高リスク変更

| 変更内容 | リスク | 対策 |
|---------|-------|------|
| Webhook URLの変更 | イベント取りこぼし | 旧URLも一定期間維持、Stripe側で両方登録 |
| PaymentIntent作成ロジックの変更 | 二重課金 | Idempotency Keyの設計を維持 |
| DB スキーマの変更（Stripe ID関連） | データ不整合 | マイグレーション時にStripeとの照合必須 |

### 7.2 中リスク変更

| 変更内容 | リスク | 対策 |
|---------|-------|------|
| フロントエンドフレームワーク変更 | Stripe.js統合の再実装 | Stripe関連ロジックを分離しておく |
| サブスクリプションプラン変更 | 既存ユーザーへの影響 | Stripe側のプラン管理機能を活用 |

### 7.3 低リスク変更

| 変更内容 | 備考 |
|---------|------|
| UIデザインの変更 | Stripe Elementsのスタイリングで対応可能 |
| 新しい決済手段の追加 | Payment Elementが自動対応 |

## 付録：用語定義

| 用語 | 定義 |
|------|------|
| PaymentIntent | 決済の「意図」を表すオブジェクト。金額・通貨・顧客情報を保持 |
| client_secret | PaymentIntentに紐づく秘密鍵。クライアントで決済確定に使用 |
| Webhook | Stripeからサーバーへの非同期通知 |
| 冪等性（Idempotency） | 同一操作を複数回実行しても結果が変わらない性質 |
| SCA | Strong Customer Authentication。欧州規制による追加認証要件 |
